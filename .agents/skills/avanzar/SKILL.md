## Primero: verificar y alinear con GitHub

Regla de Luis, 8-nov-2026. Aplica en VPS, ambos Hermes y PC local/VS Code. **El agente ejecuta la comprobación en cada inicio o reanudación de `/avanzar`; Luis no tiene que pedirla ni comparar commits a mano.** Una diferencia de SHA exige clasificar la copia; no autoriza perder trabajo ni publicar commits pendientes.

1. Localiza el repositorio por su raíz Git y remoto, sin asumir `/root/HamptonJersey` fuera de la VPS. Comprueba rama, HEAD, cambios preparados/sin preparar, archivos sin seguimiento y worktrees. Verifica que `origin` identifica exactamente `andresleosan/HamptonJersey` en github.com (HTTPS o SSH), sin imprimir credenciales que pudiera contener una URL. No cambies un remoto ajeno para hacerlo coincidir.
2. Si no existe copia, clona el repositorio canónico en una carpeta nueva y libre con `git clone --branch main https://github.com/andresleosan/HamptonJersey.git <destino>`. Nunca clones sobre una carpeta ocupada ni copies `.env`, credenciales, bases de datos o archivos privados entre equipos. En Hermes usa la ruta de proyecto admitida por el taller; si está ocupada por otro contenido, conserva la carpeta y comunica el impedimento.
3. En Hermes, toma/verifica el candado local del proyecto en **tu propio taller** **antes de fetch o cambios en una copia existente**. Si otra sesión de ese taller lo tiene, no crees otro clon para eludirlo. Para el primer clon sigue el orden permitido por `taller-claude` (clonar y después tomar candado). Conserva wrappers y autenticación; no uses otro Git ni otra ruta de publicación.
4. Desde la raíz Git, ejecuta **`node scripts/check-avanzar.mjs`** (también disponible como `npm run check:avanzar`). Lee su JSON y código de salida según la tabla inferior. Consulta `main` en GitHub mediante fetch explícito y `ls-remote`, valida el origen efectivo HTTPS/SSH y compara HEAD, main, estado de archivos y worktrees; no depende de la ruta del equipo ni de una referencia remota almacenada. Registra fecha, ruta y SHA remoto observado. Si falta el script en una copia antigua, comprueba el origen como en el paso 1, ejecuta `git fetch --no-tags --no-prune --refmap= origin refs/heads/main:refs/remotes/origin/main`, contrasta `git ls-remote --exit-code origin refs/heads/main` con `git rev-parse refs/remotes/origin/main` y clasifica HEAD con `git rev-list --left-right --count HEAD...origin/main`, estado y ancestros. Después de alinear, ejecuta el verificador de la copia actualizada. Este arranque lo realiza el agente, también desde una skill instalada antigua. Si falta Git/Node o falla el acceso, di «sincronización no verificada»; conserva el trabajo y limita la continuación a lectura/diagnóstico independiente, sin presentar la copia como actualizada ni publicar.
5. Decide según el estado comprobado:
   - **Main limpio e igual:** continúa.
   - **Main limpio y solo atrasado:** `git merge --ff-only origin/main`; repite el verificador y comprueba HEAD = SHA remoto observado.
   - **Trabajo pendiente de esta misma tarea:** consérvalo y retómalo. Si origin/main es antecesor de HEAD, la base ya incluye lo publicado aunque haya commits locales. Registra esos commits y cambios como pendientes, no como publicados. Si el remoto avanzó, integra lo nuevo en una copia de trabajo segura conservando la entrega local, resuelve conflictos y repite las pruebas afectadas; nunca abandones la tarea empezada para aparentar igualdad.
   - **Otra rama, cambios ajenos, commits pendientes de otra tarea, divergencia o repositorio equivocado:** conserva íntegra la copia. Fuera de Hermes, prepara una copia nueva desde el remoto canónico, en carpeta libre y rama main, y trabaja allí. Reutiliza un worktree existente solo si se comprueba su origen, base y ausencia de trabajo ajeno. Dentro de Hermes respeta el clon y candado obligatorios: si el taller no permite una copia aislada, deja el diagnóstico concreto sin tocar lo ajeno; no esquives esa restricción.
6. Tras alinear, lee **desde esa copia** `.agents/skills/avanzar/SKILL.md`, sus referencias, `docs/roadmap/AVANZAR.md`, ESTADO y checklist. Un arranque instalado viejo solo sirve para llegar a la versión canónica. Si la copia contiene cambios locales de esta skill de la tarea en curso, revisa ambos textos y conserva esos cambios; no los sobreescribas al actualizar.
7. Antes de editar, comunica en una línea la copia/base usadas y qué trabajo local se preservó: `Repo verificado · main · local <SHA> · GitHub <SHA> · <estado>`. No llames «idéntica» a una copia con archivos modificados o commits pendientes. GitHub no contiene cambios que otro equipo no haya publicado: no prometas sincronizarlos ni copiarlos por otro canal. No repitas la actualización mientras sigues construyendo; al reanudar la tarea o retomar otro encargo vuelve a comprobar el remoto conservando los cambios.
8. Antes de pedir aprobación de publicación repite el verificador y comprueba la integración. **Con un SHA ya aprobado**, HEAD/main quedan congelados: ejecuta `node scripts/check-avanzar.mjs --approved-sha <SHA completo aprobado>` (en Hermes también lee `TALLER_SHA_APROBADO`). Exige salida 0, HEAD/main iguales al aprobado, copia limpia y remoto igual o antecesor; si hay que integrar otro cambio, detén la publicación y prepara nueva revisión/aprobación. La sincronización nunca equivale a permiso de push, despliegue o migración.

Nunca uses `reset --hard`, `clean`, force-push, stash automático, rebase ni borrado/recreación de carpetas para «alinear». No cambies controles, permisos, credenciales, servicios ni configuración del VPS. Las operaciones reversibles de lectura, fetch, clon nuevo permitido y avance fast-forward están autorizadas por esta regla; no vuelvas a pedir permiso rutinario para ellas.

| Salida del verificador | Acción del agente |
| --- | --- |
| `0` | Main limpio e igual; continuar. En modo SHA aprobado puede haber commits locales aprobados sobre el remoto: es comprobación de integración, no prueba de publicación. |
| `2` | Estado local que requiere clasificar: cambios pendientes, adelanto, atraso, divergencia, otra rama, HEAD separado o SHA aprobado diferente. Aplicar el paso 5 y preservar el trabajo; no convertirlo en «todo sincronizado». Retomar trabajo propio actualizado no requiere pedir a Luis que compare SHAs. |
| `1` | No verificado: origen incorrecto, fallo de Git/red, remoto que cambió durante la consulta o historia insuficiente. Diagnosticar; no continuar editando como si la base estuviera comprobada. |

El verificador solo actualiza referencias remotas y consulta Git: no integra ni publica. Usa el Git del entorno y su autenticación existente. En Hermes el candado se obtiene **antes** del comando; el verificador no sustituye ese control. No se ejecuta como hook ni servicio: forma parte del procedimiento obligatorio del agente al invocar la skill.
