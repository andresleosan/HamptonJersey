`SearchVersion` es el `applicants.updated_at` ISO **opaco**, comparado por igualdad; `proposal.revision` es entero positivo. `ManualCriteriaPatch` mantiene los campos y semántica actuales de SEARCH_FIELDS/SAP-10, incluida operación cuando el PUT vigente lo admite. `ProposalCriteriaPatch` (alias `CriteriaPatch` en este documento y REG-13) es el subconjunto restringido para propuestas, mapa de campos admitidos por `criteriaDiff`/SEARCH_FIELDS de SAP-10, con exclusión adicional de identidad/categoría/operación, stage, asignación, cierre, idioma/franjas y contacto. La propuesta no cambia modalidad; el empleado vuelve al flujo manual vigente si lo necesita. Esta restricción no cambia el PUT manual ni impone una regla comercial nueva. Nuevos campos área/prioridades comerciales se habilitan solo cuando el validador integrado los soporta. Patch no es reemplazo de formulario: no mencionado conserva el valor, `null` significa borrar explícitamente y requiere fila visible de confirmación. Prioridades se fusionan por clave, conservando valores y unknown no mencionados; listas son reemplazo explícito solo del campo citado, no eliminación inferida.

## Commit, tareas y recálculo

Confirmación usa un único env.DB.batch con guard que aborta toda la transacción si applicant activo/base_version o propuesta draft/revision/expiry no coinciden; update+version monotónica, touch de contacto, marcar confirmed, evento `applicant.criteria_confirmed` entityapplicant, tarea NOT-11 y recibo. El guard aborta con constraint patrón ya utilizado por el proyecto; un UPDATE que afecte0 no puede dejar evento/recibo/cola. El evento solo `{version:1,proposal_id,fields,base_version,applied_version,source}`, actor servidor; no before/after libres, texto dictado o modelo en events. Los eventos de cambios del PUT se conservan con identidad ligada, sin dos confirmaciones para la misma operación. El segundo intento simultáneo gana el mismo recibo si clave coincide; con otra clave/propuesta obsoleta409.

La misma transacción inserta `criteria_recompute_requests(id,applicant_id,search_version,state,claim_token,lease_until,ticket_seq,attempts,error_code,created_at,updated_at)` UNIQUE(applicant_id,search_version), FKapplicantCASCADE. Es admisión durable al **evaluador existente**, no otro motor ni otra tabla de progreso. `criteriaRecomputeRequestStatements(env,{applicantId,searchVersion,requestId,at})` es componible; `runCriteriaRecomputeRequests(env,{at,limit:10}):Promise<{succeeded:number,failed:number,pending:number}>` reclama con CAS y llama al mismo `recomputeForApplicant`/despachador BUS-12 integrado. No llamar además afterSave desde este nuevo camino; el PUT comparte esta admisión solo al cambiar criterios. Actualizaciones no criterio conservan comportamiento actual hasta revisión explícita.

Ticket único EST-01 mantiene seq/inputVersion y guard final; beginFullCheck y persistencia de request.ticket_seq/claim_token se componen en el mismo batch de inicio. El ticket expone request_id/claim_token para este caller opcional; los demás callers conservan firma y comportamiento. Añadir a escrituras/finish del ticket guard de claim_token vigente; lease120s, renovar a60s solo durante trabajo activo y persistir inicio antes de evaluar. Definir `criteriaRecomputeSuccessStatement(env,{requestId,claimToken,ticketSeq,searchVersion,at}):D1PreparedStatement`, UPDATE request→succeeded condicionado a todos esos valores y estado running. El batch de resultados contiene sus escrituras, ese successStatement y la sentencia final EST-01 de full-check-success como última mutación del batch; los guardas de todas exigen request vigente y ticket asociado, y un guard final aborta si alguna no ocurrió. Resultado, requestdurable y progreso se confirman juntos. Si el proceso cae tras ese commit y antes del acuse del worker, la request ya succeeded: reconciliarla sin nuevo ticket ni nuevo recálculo. Solo una request realmente running con lease vencida puede adquirir nuevo claim/ticket; el anterior no puede publicar éxito. No usar afterSave ni callback posterior para marcar succeeded. Dos ticks no crean dos efectos ni avisos; respuesta perdida se resuelve consultando request/versión, no reaplicando criterios. Retries máximo3 para fallo cierto sin commit; `unknown` de operación remota no aplica aquí porque matching es DB, y un commit DB incierto se inspecciona por recibo/versión. Versión nueva/cierre marca superseded, nunca reabre. Fallo conserva criterios guardados y progreso previo; UI `Changes saved. Match check pending` o `Match check failed. Retry` y acción autenticada de reintentar la misma request, sin nueva confirmación. El resultado comercial solo acredita el alcance implementado por BUS-12; no llamarlo inventario completo si productor no lo prueba.

NOT-11 se integra con sentencias componibles reales: una tarea por propuesta vigente para revisión y actualización de acciones dependientes por versión, sin cancelar consultas que sirven a otros matches. Si API de NOT-11 no es componible, esa integración permanece pendiente y bloquea el tramo completo; no fingir atomicidad mediante una llamada posterior.

## IA y voz: puerto cerrado, no proveedor inventado

REG-13 define el puerto normalizado de extracción. Para voz, una segunda capacidad `transcribeCriteria` solo se implementa tras seleccionar proveedor y formatos/límites/borrado acordados. Hasta entonces no hay getUserMedia, SpeechRecognition del navegador, subida de audio ni botón funcional de dictado. No usar transcripción del sistema que pueda enviar audio a un servicio no validado. Pruebas con fixtures sintéticos validan el consumidor, no acreditan un proveedor o dictado real. Activar exige revisión de procesamiento/conservación, autenticación, clase de datos y transporte privado ya permitido, sin abrir puertos ni debilitar barreras.
