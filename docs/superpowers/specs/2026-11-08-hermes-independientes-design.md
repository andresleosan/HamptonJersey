# Hermes independientes y cuatro listas compartidas

Decisiones de Luis, 8-nov-2026: ambos Hermes deben trabajar simultáneamente en entornos separados; las columnas se llaman Lista 1 a Lista 4 y no se asignan permanentemente a herramientas. Al dejar Claude Code y próximamente GPT, el flujo elegido es Hermes con OpenCode y DeepSeek. La implementación está autorizada; una publicación nueva se revisa con su SHA concreto.

## Contrato de listas y coordinación

- Los encabezados exactos son **Lista 1, Lista 2, Lista 3 y Lista 4**. Se conservan las 250 tareas y su asignación única. Los IDs internos `vps`, `hermes`, `vscode` y `codex-desktop` siguen solo por compatibilidad; no son nombres visibles ni restringen herramientas.
- Cada lista declara capacidad dos. Un catálogo antiguo que omita `capacity` conserva capacidad uno. Las cinco identidades ejecutoras existentes pueden solicitar cualquiera de las listas sin ampliar sus roles. Un actor, sesión o checkout mantiene una sola reserva propia.
- `init --list 1..4` elige la preferencia inicial; `--slot` es el alias heredado y no se combina con `--list`. `select-list --list 1..4` permite cambiarla explícitamente, consultando primero el tablero y preservando IDs y estado local. No reserva trabajo ni acredita autorización: el servidor vuelve a comprobarla al reclamar.
- Cambiar la preferencia se rechaza con trabajo propio abierto, pausado, sin contacto o entregado, operación desconocida, aprobación o turno de publicación propios pendientes. No borrar sesiones ni reinicializar para eludirlo.
- El servidor recupera el trabajo propio y prioriza la lista seleccionada. Si no tiene una unidad viable, puede asignar ayuda temporal a otra lista; conserva la asignación original de la tarea. El tablero distingue la lista elegida del origen de la ayuda. La capacidad cuenta reservas de la lista elegida, no todas las tarjetas de otras listas que reciben ayuda.
- Las reservas pausadas o vencidas siguen ocupando plazas y recursos. El relevo comprueba capacidad excluyendo únicamente su propia reserva. Las dependencias, exclusión por tarea/recurso y turno global de publicación permanecen. Cada transición exige confirmación del servidor.

## Talleres y ejecución

Hermes 1 conserva su taller y trabajo anterior. Hermes 2 usa otro taller con home, clon, índice Git, sesión, configuración y credenciales propios. No se copia el home, autenticación ni sesiones. Cada llave SSH solo accede al taller correspondiente. El candado local protege su propia copia y no bloquea al otro Hermes. Cada taller usa puertos de prueba internos, sin abrir puertos del VPS, y conserva los controles de red, Git y publicación.

Hermes recibe el encargo; OpenCode construye y realiza la revisión en una sesión independiente, utilizando DeepSeek. Está instalado OpenCode V2 oficial `@opencode/cli@2.2.6` y se usa el helper `taller-opencode build|review [--session ID] -- <encargo>`; `--session` se limita a continuar una construcción propia. La revisión siempre es una sesión nueva sin shell. La ejecución usa `run --standalone --format json` en loopback, sin servidor compartido entre talleres. El helper fija el directorio canónico, conserva la configuración administrada y filtra secretos de stdout/stderr. Su entorno permitido excluye credenciales de Cloudflare y marcas de aprobación. Se conservan las guardas Git y el candado local; la publicación del SHA aprobado se ejecuta mediante un mandato separado de Hermes y los wrappers existentes. Cambiar el constructor no autoriza publicar.

Cada bot tiene una clave DeepSeek distinta, verificada y provisionada selectivamente en su propio taller. Cada panel admite el proveedor nativo: `Keys → DeepSeek API Key → Save`, seguido de `Models → Main Model → Change → DeepSeek → deepseek-v4-pro → Apply` y sesión nueva. El panel configura Hermes, no OpenCode. El operador aprovisiona únicamente la clave de cada bot en su almacén privado de OpenCode por el canal administrativo autorizado; no se copia el `.env` entero ni se habilita passthrough SSH. La selección del modelo de OpenCode es explícita. Una rotación o eliminación requiere revisar ambos almacenes. No se recomiendan GPT o Claude automáticamente al usuario que eligió DeepSeek.

## Aceptación y riesgos

Dos actores pueden construir tareas compatibles desde la misma lista o desde listas distintas; una tercera reserva en una lista llena, una tarea ocupada o un recurso incompatible se rechazan sin alterar el trabajo previo. Cambiar de lista preserva las identidades y nunca mueve una reserva pendiente. Ambos Hermes ejecutan simultáneamente en archivos y sesiones independientes. La publicación conserva un solo turno y requiere aprobación del SHA final intacto. Las pruebas de proveedor solo acreditan el taller y modelo efectivamente usados, sin trasladar credenciales o declarar verificados clientes ausentes. El ledger distingue resultados de cada etapa, publicación y activación.
