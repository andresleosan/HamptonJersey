**Estado:** Diseño técnico del consumidor definido; extracción real condicionada a proveedor/carril C2 y núcleo AUT-19 integrado. Texto libre existente preservado.

## Estado y alternativas

Hoy `server/applicants.js` valida y guarda `requirements` sin IA; el formulario conserva «Anything else that matters?». El texto original no se sobrescribe para sustituirlo por etiquetas. El plan anterior SAP10 resuelve confirmación; AUT19 l1b aporta propuesta/CAS/recibo. Esta entrega define el consumidor y contrato de extracción con fixtures; proveedor real y dictado siguen pendientes. No llamar construcción del tramo IA lista sin carril autorizado.

Alternativas: extracción automática y guardado directo pierde negaciones/prioridad y se descarta; regex para frases abiertas simula comprensión y se descarta; contrato de extracción limitado que produce evidencias y propuesta humana es la elección técnica propuesta. No procesa históricos automáticamente ni una inscripción pública dispara un modelo.

Construcción: EST09 integrado, BUS12design, NOT11design por tramo según catálogo y núcleo AUT19 propuesto integrado para persistir/confirmar. Activación: carril C2 autorizado alternativo Hermes validado o AUT06local, límites/retención de proveedor documentados. No se exige habilitar ambos, no enviar a Telegram ni cambiar Hermes público.

## Datos, puerto y límites propuestos

Crear `server/requirement-extraction.js`, `server/model-requirements-port.js`, `server/routes/requirement-extraction.js`, `admin/src/RequirementExtraction.jsx`. No API SDK, modelo o librería nuevo en este plan; adaptador predeterminado `disabled`, `extractRequirements` responde503 `Requirements suggestions are not enabled`. La futura implementación del proveedor requiere completar ficha de activación: responsable/versión/configuración autorizada/claseC2/retención/región/límites/transporte/autenticación/prueba real, sin secretos en Git.

`RequirementExtractionInputV1={version:1,request_id:string,search_version:string,requirements_text:string,operation:'rent'|'buy'|'transfer',search_category:'residential'|'commercial',allowed_keys:string[]}`. Excluir contacto/nombre/teléfono/email/dirección exacta/edades/otras búsquedas/archivos. Antes de crear llamada, UI advierte que el texto puede contener datos personales y pide al empleado revisar el fragmento; `requirements_text` máximo4000caracteres y debe ser fragmento seleccionado explícitamente por el empleado. No prometer anonimato por quitar nombre. Datos C3 o que excedan el alcance no se mandan al carrilC2: modo manual conserva datos y sin llamada; el gate de revisión del empleado no es una desclasificación automática.

`RequirementExtractionOutputV1={version:1,request_id:string,suggestions:Suggestion[],unresolved:{start:number,end:number,reason_code:string}[]}`; máximo20suggestions, `Suggestion={key:string,operation:'set'|'clear',value:unknown,priority:'must'|'preferred'|'unknown',evidence:{start:number,end:number},certainty:'explicit'|'ambiguous'}`. offsets son índices UTF-16 de JavaScript al texto original; 0≤start<end≤length y nunca cortan un parsurrogate. No hay snippet libre que el modelo pueda inventar: servidor deriva la cita del rango. Máximo20unresolved; reason_code allowlist ambiguous/unsupported/conflict/out_of_scope. Certainty no es score de autorización.

Puerto `extractRequirements(input,{signal}):Promise<RequirementExtractionOutputV1>` en model-requirements-port.js; hard timeout20s, sin retry automático, petición lógica única por request_id. `validateExtractionOutput(input,output):{suggestions:ValidatedSuggestion[],unresolved:Unresolved[]}` valida allowlist/rangos/tipos/esquema/citas y rechaza todo el resultado si hay campos extra, clave CRITERIA fuera de allowlist, nombre de columna usado como key, IDs incorrectos,25suggestions, HTML/URLs en lugar de valores o referencia fuera de texto. No salta la validación de validateApplicant ni acepta una operación oculta del modelo.

Allowlist inicial **residencial**: `Suggestion.key` es clave CRITERIA, nunca nombre de columna. Mapa exacto de `value` al patch (campos opcionales solo se cambian si están presentes):

| key | value en set | Patch producido |
|---|---|---|
| parking | entero≥0 validado | parking_spaces |
| area | {parishes_wanted?:string[],parishes_excluded?:string[],area_answer?:string,preferred_parish?:string|null} | solo esas claves y solo las que estén integradas/validadas por REG06; area_answer/preferred_parish no integradas→unsupported |
| type | string[] de tipos existentes | property_types |
| bedrooms | {min?:number|null,max?:number|null}, al menos una clave | bedrooms_min/max nombrados, no alterar la otra ni bedrooms_ideal |
| bathrooms | número existente validado | bathrooms_min |
| garden, terrace, balcony | true para pedir esa opción | añadir únicamente esa opción a outdoor; preservar las demás |
| furnished | enum existente | furnished |
| pets | estructura tipada admitida por validateApplicant | pets, no borrar hecho de mascotas por prioridadpreferred |
| near | texto de cita (≤límite actual) | near, sin geocodificar ni inventar distancia |

`priority` se guarda en requirement_priorities.values[Suggestion.key] con must/preferred/unknown. Se conserva el resto del mapa y unknown. unknown es **prioridad por resolver**, distinta de respuesta desconocida: no añadir key a requirement_priorities.unknown si el valor ya está respondido; ese array corresponde a respuesta no conocida según validador. La UI exige resolver prioridad antes de selección efectiva. En set resuelto retirar solo key de unknown si ahora tiene respuesta válida. garden/terrace/balcony tienen prioridad individual y se componen por opción, sin reemplazar la lista outdoor entera. Varias sugerencias distintas de esas opciones pueden componerse sin perder las anteriores. `operation:'clear'` no se preselecciona: requiere acción explícita del empleado; limpia únicamente respuesta indicada (o quita esa opción outdoor), retira solo su prioridad y su entrada unknown, y muestra todo en diff antes de confirmar. No se convierte una negación de jardín en filtro jurídico o prohibición de vivienda.

`requirements` queda **solo lectura como cita original**, fuera de todo patch REG13; tampoco lo elimina un clear. Texto no mapeable va a unresolved.unsupported y el empleado puede conservarlo tal cual. «quiet street» muestra cita sin fabricar un campo estructurado; «near Victoria College» puede proponer near con prioridadunknown. Contradicciones quedan unresolved, no gana «última frase». El núcleo AUT19 puede editar texto a mano por su flujo explícito, pero REG13 nunca sustituye ni borra el original. Categoría comercial, edades, situación legal, presupuesto inferido, cierre, contacto, idioma, modoAuto y disponibilidad están fuera de la extracción inicial. Búsquedas comerciales conservan edición manual y reciben unsupported sin llamada al modelo hasta un alcance/mapeo comercial específico; no se afirma REG13íntegro para ellas. Presupuesto manual sigue disponible en AUT19.

`buildCriteriaPatchFromSuggestions(current,selected:ReviewedSuggestion[]):CriteriaPatch` exige selected con valor/priority resueltos y validación común; solo claves seleccionadas. No cambiar una prioridad por creer que el modelo tiene confianza; no seleccionar por defecto respuestas ambiguous/unknown. Múltiples suggestions sobre misma clave no componen hasta que el empleado resuelve el conflicto; clear explícito solo si evidencia y confirmación. El resto de MUST y texto original permanecen.

## API, ciclos y privacidad

POST autenticado `/admin/applicants/:id/requirement-extractions` body `{base_version,selected_text,operation_id,reviewed_for_processing:true}`, límite16KiB/4000caracteres. En servidor obtiene operation/category/allowlist, no los confía al cliente. Comprueba asociación, búsqueda activa, versión y gate del proveedor antes de cualquier llamada. Devuelve200 resultado normalizado con base_version, expires_at y suggestions sin crear propuesta ni guardar criterios.401/403CSRF,404,409versión/cierre;400texto/revisión/esquema;503disabled;504timeout;502salida inválida;429ya en curso. Erroresfijos no incluyen texto/providerresponse. Aun con respuesta válida revalidar versión/estado al crear la propuesta, no solo al hacer la llamada.

La UI mantiene el resultado y selected_text **solo en memoria**, descarta al salir/cambiar de búsqueda/expirar10minutos, y no lo deja en local/sessionStorage/URLs/logs/analytics. El servidor no persiste prompt/respuesta/texto; nueva tabla mínima `requirement_extraction_operations(actor,operation_id,request_hash,applicant_id,base_version,state,lease_until,finished_at,created_at)` con UNIQUE(actor,operation_id), FKapplicantCASCADE, sin contenido. Hash incluye cuerpo normalizado; intento distinto misma clave409. Lease25s, statesrunning/finished/failed/unknown, limpieza24h; no se reejecuta la misma operación si terminó o perdió respuesta (409 `Start a new suggestion request`), porque no se almacena la respuesta. Retry manual explícito con clave nueva tras enseñar que puede invocar de nuevo; nada duplica un guardado porque todavía no existe. Al expirar lease de llamada incierta, unknown y no relanzar automáticamente. Timeout aborta consumidor; cualquier retorno tardío se descarta. Proveedor puede tener retención propia que exige gate y no se afirma eliminada por cerrar pestaña.

Elección de suggestions genera `CriteriaPatch` validado y POST al núcleo AUT19 con base_version y nueva operation_id; se muestra antes/después y se confirma por el mismo camino. El servidor vuelve a validar todos los valores y prioridades; el resultado del modelo no puede llamar confirm. Eventos mínimos `applicant.requirements_suggested` sin texto (solo request_id/campos/versión) dentro del registro de finalización; dicho evento informa propuesta, no evidencia de conversación ni datos guardados. Cierre concurrente descarta propuesta sin reabrir búsqueda.
