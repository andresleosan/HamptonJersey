# PUB-10 · Registro de propietarios · plan de implementación

> Para agentes: usar `superpowers:executing-plans`. Plan documental; no activar el formulario durante planificación.

**Objetivo:** que propietarios soliciten a Hampton vender o alquilar y, si quieren, una valoración. **Spec:** [tanda6](../specs/2026-11-10-tanda6-propietarios-design.md). PRE-03 y PRE-09 son condiciones para activar recepción real; se puede construir desactivado.

## Modelo y contrato

- [ ] Crear migración siguiente ordinal libre con `owner_requests`: id UUID PK; name,phone,email,address TEXT NOT NULL; operation CHECK sale/rent; valuation_requested CHECK0/1; status CHECK new/contacted/closed; created_at,updated_at; privacidad version referencia obligatoria; índice status/created_at/id. No fusionar silenciosamente con contactos de buscadores ni propietarios de Rentals. No crear una vivienda ni una cita por el registro.
- [ ] `owner_request_receipts`: request_id generado en cliente como PK, owner_request_id UNIQUE con FK a owner_requests, payload_hash y fecha. Un solo recibo guarda identidad de operación. Hash SHA-256 de JSON canónico con campos normalizados name/phone/email/address/operation/valuation_requested/privacy_version ordenados y UTF-8; excluir Turnstile y request_id. Guardar solo en base privada, nunca exponer hash. Separar recepción nueva de repetición de transporte: mismo ID/mismo payload devuelve misma respuesta; mismo ID/diferente payload409. Dos peticiones con ID diferentes de igual correo crean dos solicitudes para revisión del equipo, sin revelar si alguien existe.
- [ ] Añadir soporte de entidad `owner_request` al CHECK `events.entity_type` y al CHECK `notifications.target_kind` desde últimas migraciones acumuladas, conservando triggers/índices/datos; validar targetExists por ID UUID, sourceAllowsTarget y enlaces al detalle. Un único D1 batch guarda solicitud, recibo, evento con ID/operación/flag valoración sin datos personales y task `Contact property owner` con `task_key=owner-request:<id>`. El INSERT ganador vuelve a comprobar en SQL la bandera habilitada y la versión de aviso actual después de Turnstile: cambio concurrente/desactivación ->409/503 sin solicitud ni evento. Insert solicitud/recibo/evento/tarea condicionado al ganador mediante trigger con comprobación de unicidad; D1 batch con INSERT sin cambios no debe generar evento/tarea adicional, y no depender de changes() después de sentencia intermedia. Una carrera con mismo request_id produce una sola solicitud, recibo, evento y tarea; payload distinto409. Todas las rutas Staff comprueban sesión y protegen mutations con sameOrigin.
- [ ] POST `/api/owner-requests`: JSON <=8KiB, request_id UUID, name 1..120, phone 5..40, email 3..254 válido, address 5..400, operation sale/rent, valuation_requested boolean y turno Turnstile. Trim y normalización de validadores existentes, sin interpolar SQL. Falta de nombre/teléfono/correo/dirección/operación ->400 por campo; no asumir dirección de persona como identidad. Rechazar campos extra salvo token y versión autorizada de aviso. Respuesta 201 `{ok:true}` y 200 replay con mismo cuerpo, sin datos ni detalles de coincidencia.
- [ ] Formulario genera request_id al iniciar, lo conserva en memoria para reintentar un envío incierto sin guardar PII en localStorage; tras recarga se necesita nuevo ID y puede llegar una solicitud duplicada, que Staff revisa. Validar antes de gastar Turnstile; ante respuesta incierta, repetir con nueva comprobación anti-spam y mismo request_id, con fast-path seguro para recibo ya existente antes de verificar token; mismo ID/payload solo retorna éxito genérico, sin devolver datos. Desactivar recepción antes de verificar token si configuración de privacidad no está habilitada.
- [ ] Bandera `owner_enquiries_enabled=false` por defecto. Cliente no muestra formulario activo cuando false; servidor devuelve503 aunque se eluda UI. Habilitación solo cuando Hampton confirme PRE-03 y aviso PRE-09 aprobado y publicado, referencia/version almacenada. No inventar aviso legal ni consentimiento de marketing; enlace visible al aviso real y separarlo de marketing. No activar ni cambiar cuentas durante esta planificación.
