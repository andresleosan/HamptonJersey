F0 §5 y §9 conserva ese compromiso como texto editable; el plazo se restituyó en una pasada posterior. El resto de este documento registra la entrega y las pruebas históricas de aquel momento.

Base de trabajo: `dd63b56e59aa2098c4d2c33813526b7cac0fc89b`. REG-12 **permanece parcial**. Este tramo no modifica el catálogo, no aplica migraciones y no activa servicios externos.

## Entregado

- El mismo acuse público se muestra después de cualquier respuesta satisfactoria, sin nombre, indicación de registro repetido ni resultados. Se elimina el plazo de un día no acreditado. El texto es más prudente que la propuesta del plan: pide revisión del equipo sin anunciar una búsqueda activa, pues el mismo acuse se usa para comercial, que no dispone de matching automático. Las solicitudes repetidas siguen el circuito existente de evento y aviso para el equipo y no reabren búsquedas anteriores. La respuesta de la API conserva `201 {ok:true}`. La igualdad de respuesta no demuestra tiempo constante.
- En Requirements de una búsqueda residencial activa, una lista calculada a partir del registro guardado señala must-haves sin respuesta y prioridades explícitamente desconocidas con respuesta. Prioridades ausentes o no válidas producen una indicación agregada, no una conversión a opcional. Los controles enfocan el campo o su prioridad; los cambios sin guardar no reemplazan la instantánea mostrada. No hay lectura, escritura, endpoint, polling ni tabla nuevos.
- Residencial excluye de este cálculo los criterios no aplicables y los opcionales sin respuesta; una lista vacía no es una declaración de que la ficha esté completa. Comercial y operaciones desconocidas no se evalúan con reglas residenciales. La vista se omite en búsquedas archivadas, resueltas y pendientes de revisión.

## Alcance y dependencias que siguen abiertas

- `recomputeForApplicant` se sigue programando después del acuse, sin que esta entrega pruebe que terminó ni que tuvo éxito. Falta el productor EST-01 para distinguir ejecución, fallo, versión obsoleta y resultado actual; tampoco se ha implementado aquí el contrato de API `registration_result` del plan. No se presenta un cero ni se crean marcas de progreso ficticias.
- BUS-01 aún no acredita el inventario común y fuentes externas, y BUS-12 no acredita aquí la clasificación actual. Quedan pendientes el resultado inicial fiable por búsqueda, los contadores verificados, las carreras y la cobertura comerciales previstas por el plan. Para solicitudes de dos operaciones sigue siendo necesario verificar cada resultado de forma independiente.
- El helper detecta metadatos de prioridades ausentes o mal formados cuando recibe el objeto, pero el lector y editor existentes pueden fallar antes si la fila histórica contiene JSON inválido o una estructura incompatible. Esta entrega no repara ni reescribe datos históricos ni prueba esa recuperación de extremo a extremo.
- Una prioridad histórica `unknown` puede aparecer con el interruptor del editor en Off, aunque la indicación nueva la señala como pendiente y no la llama opcional. La interfaz anterior requiere una reconciliación accesible de ese estado; la nueva indicación no cambia la prioridad por sí misma. El recorrido local cambió el presupuesto y comprobó que la API siguió devolviendo la prioridad `unknown`.
- El listado refleja solo criterios guardados del propio registro; no usa las asociaciones de visitas de Timeline, no envía comunicaciones, y no prueba un despliegue ni el estado remoto.
